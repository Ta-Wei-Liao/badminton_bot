# 可分享的視窗版搶場地程式設計

日期：2026-11-14
狀態：待實作

## 1. 背景與動機

這支程式目前只有作者自己用：在終端機裡 `python -m badminton_bot.main`，一題一題回答，
固定在週四 00:00 搶中正羽球 7-4 的 20:00、21:00 兩格。

作者想把它分享給一起打球的球友。球友**不是軟體工程師**，不會跑 Python；
他們有的用 macOS、有的用 Windows。所以這次要改三件事：

1. 中山運動中心先停用（選單上看得到，但不能選，後面標「暫時停止」）。
2. 中正的搶法變彈性：**哪天打開程式就搶哪天**，**場地、時段都能多選**。
3. 做成**雙擊就能執行**的視窗程式，透過 GitHub 下載頁發給球友。

> 這推翻了 2026-09-06 延遲優化設計裡「多場地並發不在範圍內」的非目標。
> 當時只有作者一人、只要 7-4；現在的使用者是一群人。

## 2. 目標、非目標、反目標

### 目標

1. 球友從 GitHub 下載頁下載、解壓、雙擊，就能看到中文視窗並完成一次搶場地。
2. 球友可多選場地與時段，程式在開放瞬間**同時送出全部組合**，搶到幾個算幾個。
3. 開搶日期由「按下開始的當下」自動決定，不需要球友懂任何日期規則。
4. 現有的時序機制（T−3 分登入、伺服器校時、NTP 重測、預熱、事後偵察）完整保留。

### 非目標

- 羽3-1～羽3-4（編號未知，見 §4.2）。
- 中山運動中心的任何功能修改（只是停用）。
- 程式碼簽章／公證（要年費，球友多按一次「仍要開啟」即可）。
- 自動更新、記住密碼、排程好幾週。
- 繞過或破解網站的 Cloudflare Turnstile 人機驗證（見 §7）。
- Intel Mac（見 §6.1）。

### 反目標（做了就算失敗，即使「能跑」）

- **害球友的帳號被封**。這是別人的真實帳號，比作者自己的更不能冒險。
  所以有請求數上限（§4.3），而且不能有任何重試、迴圈或額外的請求。
- 密碼出現在任何檔案裡（log、設定檔）。
- 球友看不懂結果：搶到沒搶到，必須一眼看出來，不能藏在 log 裡。
- 倒數期間電腦睡著，導致錯過開搶。

## 3. 使用者看到的樣子

### 3.1 表單（按「開始」之前）

由上而下：

- **運動中心**：下拉選單。「中正運動中心」可選、預設選中；
  「中山運動中心（暫時停止）」灰色不能選。
- **身分證字號**、**密碼**（密碼欄以 `•` 遮蔽）。
- **場地**：五個勾選框，羽球7-1 ～ 羽球7-5。
- **時段**：16 個勾選框，06:00–07:00 ～ 21:00–22:00。
- **摘要列**：即時顯示「已選 N 片 × M 時段 ＝ K 個請求（上限 12）」，
  以及「將於 11/19（四）00:00 開搶，預約 11/26（四）的場地」。
- **開始** 按鈕：未填帳密、場地或時段沒選、或 K > 12 時不能按，原因直接寫在摘要列。

### 3.2 執行中（按下「開始」之後）

- 表單全部鎖住。
- 大字顯示目前階段與倒數，例如「等待登入（還有 2 小時 13 分）」→「已登入，校時中」→
  「倒數 5 秒」→「已送出，等待回應」→「完成」。
- 下方一個捲動文字框，顯示精簡過的中文 log（與檔案 log 同源，但不含密碼——本來就不會有）。
- **取消** 按鈕：在送出前任何時刻都可以按，程式停下、登出（若已登入）、表單解鎖。
  送出後按鈕失效（請求已經出去，取消沒有意義）。
- 關閉視窗時若正在執行，先問「確定要放棄這次搶場地嗎？」。

### 3.3 結果

一張表：列是場地、欄是時段，每格顯示 ✅ 搶到 / ❌ 沒搶到 / ⚠️ 無法判斷。
表下方一句總結：「搶到 3 / 6 格」。另附一行「log 檔位置：…」並提供「打開 log 資料夾」按鈕，
方便球友把檔案傳給作者看。

## 4. 搶場地規則

### 4.1 日期

按下「開始」的那一刻記為 `now`：

- 開搶時刻 `open_at` = `now` 之後的**第一個台北時間**午夜 00:00。
  一律用固定的 UTC+8 計算，不看球友電腦的時區設定（網站是在台北午夜開放；台灣沒有夏令時間，
  所以固定偏移就夠，Windows 上也不需要額外安裝 `tzdata`）。畫面上的日期也以台北時間顯示。
  這是作者這邊的判斷。
- 預約日期 = `open_at` 的日期 + `booking_window_days`（中正為 7）。

例：週三 21:00 按開始 → 週四 00:00 開搶 → 預約下週四。週四 00:05 按開始 → 週五 00:00 開搶。

畫面上一律寫明兩個日期讓球友自己確認。若 `now` 距離 `open_at` 不到 4 分鐘，
仍照常執行（登入會立刻發生、校時探測會退化成沒有量測），但摘要列顯示警告
「距離開搶太近，校時可能不準」。

原本的 `BOOKING_WEEKDAY` 常數移除。

### 4.2 場地

中正只開放這五片，名稱與 QPid：

| 名稱 | QPid | 來源 |
|---|---|---|
| 羽球7-1 | 1196 | 2026-11-14 從頁面直接讀到 |
| 羽球7-2 | 1197 | 2026-11-14 從頁面直接讀到 |
| 羽球7-3 | 1198 | 依序推論，**未驗證** |
| 羽球7-4 | 1199 | 2026-11-14 從頁面直接讀到；也是過去成功訂到的那片 |
| 羽球7-5 | 1200 | 依序推論，**未驗證** |

場地清單寫死在中正的 service 類別上（取代現在的單一 `target_qpid`），
以後補上羽3 只要加幾行。羽3-1～3-4 這次不開放，因為只有「可預約」的格子才會在頁面上
寫出 QPid，而作者存下的那頁羽3 全被訂走了。

推論的兩個 QPid 若是錯的，最糟情況是那幾格回 `X=2` 或無法判讀，不會訂到別的東西
（QPid 屬於中正羽球的連號範圍）。之後有機會從頁面上讀到時再確認。

### 4.3 時段與請求數

- 時段為 06 ～ 21 點起始，共 16 格（頁面顯示 06:00~22:00；週末是否不同未驗證）。
- 送出的請求 = 所選場地 × 所選時段的**每一個組合**，全部在開放瞬間同時送出。
- **上限 12 個**（作者決定）。GUI 擋，核心邏輯也要再擋一次（防止 GUI 以外的呼叫繞過）。
- 沒有優先順序、沒有「搶到一片就停」、沒有重試。
- 網站是否限制每個帳號可訂的格數：作者不清楚（2026-11-14）。上限維持 12，結果表照實顯示成功／失敗／無法判斷，不另外區分「超過額度」。

### 4.4 時序（維持現狀，只把 2 個請求推廣成 N 個）

- T−3 分 Selenium 登入、取 cookies。
- 登入後到 T−30 秒做伺服器校時探測（中正實務上第一發就放棄改用 NTP，維持現狀）。
- T−40 秒開放前偵察、T−20 秒重測 NTP、T−10 秒預熱、計算送出時刻、同時放出全部請求。
- 開放後 45 秒做一次事後偵察，記錄每個所選 (場地, 時段) 的狀態。
- **連線池與預熱必須跟著 N 調整**：現在 `CONNECTION_LIMIT = 10`，低於 12，會讓部分請求
  在開放瞬間排隊等連線。上限至少要大於最大請求數。預熱也應暖好與請求數相同數量的連線
  （aiohttp 是 HTTP/1.1，一條連線一次只跑一個請求），每條連線抓一個**不同**的靜態資源，
  都由 Cloudflare 邊緣回應，不碰應用伺服器。
  這是作者這邊的判斷：瀏覽器打開一頁本來就會平行抓十幾個資源，看起來是正常流量。
  以下 15 個路徑是 2026-11-14 從中正列表頁的 HTML 直接讀出來的（同一主機
  `https://bwd.xuanen.com.tw`），足夠 12 條連線各用一個：
  `/img/place01.png`、`/img/place02.png`、`/img/LOGO/logo_wd27.png`、
  `/css/layout.css`、`/css/funtitle.css`、`/css/csspin/csspin.css`、
  `/js/tablesorter/style.css`、`/script/jquery-ui.min.css`、`/script/jquery.layout-1.4.3.css`、
  `/Scripts/sweetalert2.min.css`、`/Scripts/sweetalert2.all.min.js`、
  `/Scripts/jquery-3.6.0.min.js`、`/Scripts/jquery-migrate-3.4.1.min.js`、
  `/Scripts/jquery-ui-1.13.0.min.js`、`/Scripts/jquery.layout-1.4.3.js`。
  請求 N 個就暖 N 條（至少 2 條，維持現狀）。

## 5. 程式結構

### 5.1 把流程從 `input()` 裡拆出來

現在 `main()` 把提問、確認、時序全部混在一起。改成：

- **純邏輯**（可離線測試）：開搶時刻計算、請求組合展開與上限檢查、結果整理成表格資料。
- **搶場地引擎**：吃一個設定物件（帳號、密碼、service 類別、場地清單、時段清單、
  開搶時刻、預約日期），跑完整時序，回傳每個 (場地, 時段) 的結果。
  透過回呼或佇列回報「目前階段」與 log，支援取消。不呼叫 `input()`、不碰任何 UI。
- **GUI**：tkinter。主執行緒跑 Tk，引擎在背景執行緒裡跑自己的 asyncio event loop；
  log 透過 `logging.Handler` 丟進 queue，Tk 用 `after()` 輪詢取出顯示。

取消：倒數用的 `sleep_then_spin` / `count_down` 需要能被一個 `threading.Event` 中斷。
最後 busy-wait 的那 0.3～5 秒之內不需要支援取消。

注意 GIL：引擎在最後幾秒 busy-wait 時，Tk 執行緒的更新會搶 GIL，可能讓送出時刻晚幾毫秒。
最後幾秒 UI 只更新倒數數字，不要做重繪表格之類的重工作。

### 5.2 service 層

- `target_qpid` 類別屬性改為場地清單（名稱 + QPid）。`__init_subclass__` 的必要屬性跟著改，
  相關測試一起改。中山保留它唯一的 QPid 84，只是在 GUI 停用。
- `_generate_booking_url` 加上 `qpid` 參數，不再讀類別屬性。
- `parse_slot_state` 改成查指定 QPid。
- `BookingAttempt` 加上場地資訊，結果才能對回表格。
- 中山停用的方式：`WEBSERVICE_MAPPING`（或取代它的結構）上加一個「是否可選」的標記，
  GUI 依此反灰，引擎也拒絕執行被停用的中心。

### 5.3 開發測試模式

球友的畫面上**不出現**。設定環境變數 `BADMINTON_BOT_DEV=1` 再啟動 GUI 時，
表單多出兩欄：自訂開搶時刻、自訂預約日期。其餘流程與正式模式完全相同
（CLAUDE.md 對 dev 模式的警告照舊適用：它會真的送出 `StepFlag=25`）。

終端機版的 `main()` 提問流程移除，`python -m badminton_bot.main` 改為啟動 GUI。
CLAUDE.md 裡描述終端機提問、`get_valid_input` 慣例、`BOOKING_WEEKDAY`、
「hours are hardcoded to 20:00 and 21:00」等段落要一併更新。
`input_helper.py` 裡已不再被使用的函式可以刪掉，連同其測試。

### 5.4 log

- 位置改為 `~/Documents/badminton_bot_logs/`（Mac、Windows 皆同，用 `Path.home()`）。
  不放在程式旁邊：`.app` 內部不該寫入，而且重新打包會被清掉。
- 照舊用 `logging.FileHandler`；密碼永遠不進 logging。原本 CLI 確認畫面會印出密碼，
  GUI 沒有這種畫面，風險隨之消失。

### 5.5 防止睡眠

按下「開始」後到流程結束（或取消）期間：

- macOS：啟動子行程 `caffeinate -i -w <本程式 pid>`，結束時終止它。
- Windows：`ctypes.windll.kernel32.SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)`，
  結束時還原。

這擋不住「筆電闔上螢幕」——使用說明要寫清楚：插電、不要闔上。

## 6. 打包與發佈

### 6.1 建置

- PyInstaller 無法跨平台編譯，所以用 GitHub Actions：推送 `v*` 標籤時，
  在 `macos-14`（Apple Silicon）與 `windows-latest` 上各建置一次，
  壓成 zip 上傳到該版本的 GitHub Release。
- Mac 產出 `--windowed` 的 `.app`；Windows 產出 `--windowed` 的資料夾（內含 `.exe`），
  不用 `--onefile`（啟動慢、易被防毒誤判）。
- 只做 Apple Silicon 版。Intel Mac 已經停產多年，有需要再加——這是作者這邊的判斷。
- `bundling_scripts.sh` 同步更新成同一套參數，供作者在本機建置。
- 版本號顯示在視窗標題，方便球友回報問題時說明版本。

### 6.2 本機環境的前提

作者的 pyenv `badminton_bot`（Python 3.11.4）**沒有編入 tkinter**
（`import tkinter` 會 `ModuleNotFoundError: _tkinter`）。在本機開發 GUI 前，
需要 `brew install tcl-tk` 後重新編譯 pyenv 的 3.11.4 並重建 virtualenv。
作者已同意（2026-11-14）照這個方式重建，環境名稱與 CLAUDE.md 的指令維持不變。CI 用 `actions/setup-python`，本身就帶 tkinter。

### 6.3 球友端的前提

- 電腦要裝 **Google Chrome**（登入靠它）。chromedriver 由 Selenium Manager 自動下載，
  第一次執行需要網路。
- **按下「開始」時立刻做一次瀏覽器自我檢查**：啟動 headless Chrome、開 `about:blank`、關掉，
  完全不連預約網站。目的是讓「沒裝 Chrome」或「chromedriver 下載失敗」在按下開始的當下
  就用中文告訴球友，而不是等到 T−3 分登入時才發現、直接錯過開搶。檢查失敗就不進入倒數，
  表單解鎖。這是作者這邊的判斷。
- 未簽章，第一次開啟一定會被擋：
  - macOS：「無法確認開發者」→「系統設定 → 隱私權與安全性」→ 按「強制打開」。
  - Windows：SmartScreen「Windows 已保護您的電腦」→「其他資訊」→「仍要執行」。

### 6.4 使用說明

寫一份給球友看的中文說明（放在 README，並在 Release 說明中附連結）：下載、解壓、
第一次開啟的放行步驟、要裝 Chrome、插電不闔蓋、怎麼看結果、log 在哪、出事傳什麼給作者。
說明以文字步驟為主；截圖由作者之後自行補上。

## 7. 已知風險：Cloudflare Turnstile

2026-11-14 存下的列表頁顯示，網站的預約按鈕現在會先取得 Turnstile token、
POST 到 `/api/api_captcha.aspx` 驗證成功，才導向 `StepFlag=25`。
本程式直接 GET `StepFlag=25`，沒有經過這一步。

- 2026-11-05 的執行兩格都成功，表示至少當時伺服器沒有強制檢查。
- 2026-11-12 兩格都回 `X=2`，與「被搶走」無法區分。

本設計不處理這件事，也不嘗試繞過驗證。若伺服器開始強制檢查，這支程式（含現有版本）
會整體失效，屆時另議。結果表的「⚠️ 無法判斷」會照實呈現非預期的回應。

## 8. 測試

照 CLAUDE.md 的原則，全部離線：

- 開搶時刻計算：各星期幾、剛過午夜、接近午夜、跨月跨年。
- 組合展開與上限：0 個、12 個、13 個。
- 多 QPid 的網址產生、`parse_slot_state` 依 QPid 查詢。
- 引擎在假的 service／session 下跑完整流程（縮短時間），驗證 N 個請求同時放出、
  結果正確對回 (場地, 時段)、取消能在送出前生效。
- 被停用的中心會被引擎拒絕。
- GUI 本身不做自動化測試；作者手動在 Mac 上跑一次，Windows 版由 CI 建置後找一位球友試開。
- 實站驗證只做一次正式搶場地，遵守 CLAUDE.md 的實站限制。
