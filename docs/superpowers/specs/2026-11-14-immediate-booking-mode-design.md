# 立即預約模式 設計

日期：2026-11-14　狀態：待作者確認

## 1. 目的與背景

v1.0.2 只能「搶午夜」：按下開始後等到下一個台北午夜，送出 7 天後那天的預約。
作者希望球友也能用同一支程式做兩件事：

1. **白天訂已經開放、還空著的場地**：選好就馬上送出，不必再到網站手動點。
2. **實戰前演練**：在真正搶午夜之前，用一次立即預約確認自己的帳號、Chrome、網路都能成功預約。

第 2 點不需要另外的功能：立即預約成功，就證明了登入與預約這條路是通的。沒驗證到的只有
「午夜準時送出」，那部分與個人電腦關係不大，作者已實測過（v1.0.2 預演 +1.3 毫秒）。

**重要事實**：立即預約會真的訂下場地，不是模擬。介面與文件必須讓這一點毫無歧義。

## 2. 目標

- 表單最上方加一個二選一切換：「搶午夜」（預設）與「立即預約」。
- 「搶午夜」的行為、畫面與送出的請求和 v1.0.2 完全一樣。
- 「立即預約」：選日期、場地、時段，按開始並確認後，登入並立刻同時送出全部預約請求。

## 3. 非目標

- 讓球友自訂開搶時刻（作者已明確只要兩種模式）。
- 失敗自動重試、排程、迴圈預約。
- 限制兩次執行的間隔（作者選擇「只顯示提醒」）。
- 處理或繞過 Cloudflare Turnstile（沿用既有立場，見 2026-11-14-shareable-gui-flexible-booking-design.md §7）。
- 重新開放中山運動中心。

## 4. 反目標（做出來就算失敗的情況）

- 球友以為「立即預約／演練」不會真的訂，結果多訂或訂錯日期。
- 「搶午夜」的時序、請求數或結果因為這次改動而改變。
- 立即預約比必要的多打網站（例如沿用校時探測、預熱、偵察）。

## 5. 作者已決定的事

| 項目 | 決定 |
|---|---|
| 模式 | 只有「搶午夜」與「立即預約」兩種，預設搶午夜 |
| 立即預約的時機 | 按下開始、確認後立即登入並送出，不倒數 |
| 重複使用的防護 | 只顯示提醒，不擋 |
| 演練 | 用立即預約達成，不另做「自訂時間」 |

## 6. 我（Claude）替作者決定的事 —— 請檢查

1. **切換元件**：表單最上方一組兩個 radio button，文字「搶午夜」「立即預約」。執行中鎖住。
2. **日期選擇**：立即預約模式顯示「預約日期」下拉選單（唯讀 Combobox），選項為台北時間今天起
   到今天 + `booking_window_days`（中正 7）共 8 天，格式沿用 `_fmt`，例如 `11/14（六）今天`。
   預設選今天。搶午夜模式隱藏此欄。
3. **已過去的時段**：選的是今天時，開始時間 ≤ 現在（台北）的時段不能勾（Checkbutton disabled，
   已勾的自動取消）。開始前與送出前都再檢查一次；表單開著跨過整點時，依每秒的 `_tick` 更新。
   網站是否還有「需提前 N 小時」之類的限制不得而知，不猜；網站拒絕時結果表照實顯示失敗。
4. **上限**：場地 × 時段一樣最多 `MAX_REQUESTS = 12`。
5. **確認視窗**：只在立即預約按開始時跳出（搶午夜不加，維持現狀）。內容列出日期與每一筆
   「羽球7-2 06:00–07:00」，並寫明「按下確定會真的預約這些場地」，按鈕「確定預約」/「取消」。
6. **提醒文字**（作者要的「顯示提醒」）：立即預約模式下表單固定顯示一行橘色提醒：
   「立即預約會真的訂下場地；請勿短時間內反覆送出，頻繁登入可能導致帳號被停權。」
   確認視窗也重複這句。
7. **摘要列**：立即預約時顯示「已選 N 片 × M 時段 ＝ K 個請求（上限 12）｜立即預約 11/16（一）的場地」。
   不顯示「距離開搶太近」的警告。
8. **引擎流程（立即預約）**：瀏覽器自我檢查 → `keep_awake` → 登入 → 取 cookie、建 session →
   立刻以 `asyncio.gather` 同時送出 N 個預約 GET → 結果 → 登出、關 Chrome。
   **不做**：NTP、伺服器校時探測、開放前檢查、預熱、倒數、事後偵察。
   對網站的請求只有：登入流程 + N 個預約 GET + 登出。
   沿用 `run_booking_race` 的「先全部備妥再一次放行」機制，以 `send_at_epoch = 現在` 立即放行，
   確保結果格式、`fired` 標記、取消語意與搶午夜一致。
9. **取消**：與搶午夜相同 —— 送出前（含登入中）可取消，送出後不可。
10. **資料模型**：`GrabConfig` 加 `mode` 欄位（`GrabMode.MIDNIGHT` / `GrabMode.IMMEDIATE`），
    `open_at` 僅搶午夜使用（立即預約時為 `None`）。引擎依 `mode` 分流；
    立即預約也重新檢查：日期在可預約範圍內、沒有已過去的時段、≤ 12 筆，不合格就拋 `ValueError`。
11. **純邏輯放 `booking_plan.py`**：可選日期清單、某日可勾的時段、立即預約的驗證與摘要文字，
    都是可離線測試的純函式，GUI 只負責顯示，引擎重新檢查同一套規則（沿用既有慣例）。
12. **開發模式（`BADMINTON_BOT_DEV=1`）**：保留不動。兩個開發欄位只在「搶午夜」時顯示並生效。
13. **狀態文字**：立即預約執行中依序顯示「檢查瀏覽器…」「登入中…」「送出中…」「完成」，
    沿用既有的 stage 機制，不顯示倒數。
14. **文件**：README 使用說明加「立即預約」一節（含如何用它在搶午夜前演練、訂到的演練場記得取消、
    勿反覆送出），CLAUDE.md 同步更新兩種模式與立即預約的請求數。
15. **版本**：`__version__` 升為 `1.1.0`，另依既有流程發布。

## 7. 限制

- 線上網站限制（CLAUDE.md）：開發與測試一律離線；實站只做最後一次確認，且只勾 1 片 × 1 小時。
- 密碼不得進入 log、repr、錯誤訊息；錯誤一律用 `describe_error`。
- GUI 文字、log、註解用繁體中文；docstring 與識別字用英文。
- 背景執行緒不得直接碰 Tk，經由既有佇列回報。
- 日期一律以台北時間（`TAIPEI`）計算，與本機時區無關。

## 8. 留給實作者的事

- radio button、下拉選單、提醒文字在版面中的確切位置與間距。
- `GrabMode` 用 `Enum` 或字串常數。
- 立即預約的 stage 常數是否沿用既有的 `STAGE_*` 或新增。
- 測試的切分方式，只要涵蓋 §6 的規則（日期範圍、已過去時段、上限、引擎不呼叫校時/預熱/偵察、
  搶午夜行為不變）。
